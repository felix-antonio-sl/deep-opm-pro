# Roadmap — dirección vigente de opforja

**Fecha base:** 2026-08-09

**Horizonte:** próximo corte de producto respaldado por evidencia

El estado verificado vive en el [handoff](../../HANDOFF.md), que conserva su fecha de
corte dentro del documento.
Este documento contiene dirección y criterios de apertura; no repite cierres ni funciona
como bitácora.

## Dirección

No hay una iniciativa funcional abierta que deba ejecutarse automáticamente. El siguiente
corte debe partir de una de estas tres señales:

1. un bug reproducible que afecte modelamiento, persistencia, comprensión o recuperación;
2. evidencia de uso real que muestre fricción o una decisión mal soportada;
3. una decisión explícita del operador sobre una capacidad ausente ya declarada.

La prioridad es reducir el tiempo entre intención de modelar y valor validado, sin ampliar
el producto por inventario técnico ni reabrir frentes ya cerrados.

## Candidatos no calendarizados

| Candidato | Condición de apertura | Evidencia mínima de cierre |
|---|---|---|
| out-zoom | un modelo o flujo nombrado lo necesita | roundtrip, preservación de frontera, UX observada y compatibilidad de persistencia |
| abanicos fuera de `R-FAN-5A` | nueva regla SSOT versionada o caso general aprobado | forward/reverse, diagnóstico fail-closed y casos límite |
| probabilidad declarada sin pesos | intención de simulación nombrada | variante de modelo, serialización, UI, OPL y diagnóstico coherentes |
| auth/tenants v2 | necesidad multiusuario concreta | roles, invitación, aislamiento, rollback y operación documentada |
| coedición | colaboración simultánea real | política de conflicto/merge explícita y recuperación sin pérdida silenciosa |
| láminas didácticas OPD | necesidad pedagógica priorizada | fuente canónica reproducible y render headless verificable |
| evolución del Anclaje | caso de uso que exceda Calcar/Anclar/Soltar actuales | contrato de identidad, mutación, OPL/render y recuperación |
| GAPs visuales del canon | incumplimiento de gate o fricción observada | gobierno visual, pruebas focales y smoke de interacción |

Estos candidatos no son compromisos ni un orden temporal. La selección corresponde al
problema que produzca mayor valor verificable con el menor blast radius.

## Decisiones que permanecen cerradas

- No ejecutar un macro-refactor sin dolor medido o una capacidad bloqueada.
- No reabrir el ciclo Taller/Modelos, Apunte/Modelo o Boceto/OPD integrado sin regresión.
- No convertir observaciones estéticas sin evidencia en backlog.
- No tratar un caso de dominio externo como prioridad o contrato de opforja.
- No convertir una firma observable en afirmación de equivalencia matemática más fuerte.
- No presentar commit, push, deploy y promoción de modelos como un mismo gate.

## Gates por tipo de corte

| Cambio | Gate mínimo |
|---|---|
| documentación | enlaces activos, fechas ISO, punteros exactos, una versión por especie y revisión de diff |
| código | `cd app && bun run check` |
| visual o interacción | check, lint, build, `design:governance` y E2E afectados |
| persistencia | pruebas focales, PostgreSQL aislado, conflicto y rollback; nunca mutar producción para validar |
| arquitectura o refactor transversal | `bun run gate:refactor` y revisión de dependencias |
| canon o corpus | flujo KORA, re-pin de puentes, corpus reproducible y `bun run cordon:skill` |
| despliegue autorizado | backup, `./deploy/deploy.sh`, salud, SHA visible y cordón postdeploy |

## Criterios de selección

1. Nombrar beneficiario y decisión que mejora.
2. Formular un resultado observable y falsable.
3. Elegir el menor incremento vertical que cierre comportamiento real.
4. Mantener publicación Git, despliegue y promoción externa como decisiones separadas.
5. Actualizar `HANDOFF.md` con la nueva fecha de corte; no acumular historia aquí.
6. Para actualizar este roadmap, crear `roadmap-AAAA-MM-DD.md`, mover esta versión a
   `_archivo/` y actualizar `README.md`.
